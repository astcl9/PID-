# PID 历史数据可视化与运行分析平台企划书

**版本**：V0.2（项目现状版）  
**编制日期**：2026 年 9 月 17 日  
**项目形态**：局域网部署的 Web 数据分析工具

## 一、项目概述

本项目建设一个面向过程控制、仪表和工艺分析人员的 PID 历史数据可视化平台。平台将 CSV/XLSX 格式的历史采样数据导入后，按日期组织数据，提供年度运行日历、单日曲线、日内时间窗口、PV/SV/MV 信号筛选、智能运行分段和数据导出能力。

项目采用 FastAPI 提供后端服务，使用 Parquet + DuckDB 作为本地开发和回退存储方案，并提供 PostgreSQL 作为大规模历史数据的部署方案，同时保留 ClickHouse 兼容路径。系统可运行在 Windows 或 Docker 环境中，支持局域网内多终端访问。

## 二、建设背景与问题

传统 PID 历史数据通常以分散的 CSV、Excel 文件保存，存在以下问题：

- 文件体量大，直接用 Excel 或一次性加载 DataFrame 容易造成内存压力；
- 按天、按回路查找运行状态效率低，难以快速定位异常时段；
- PV、SV/SP、MV 信号缺少统一展示，趋势和设定值变化不易对照；
- 原始采样点数量过多，浏览器无法直接承载全年数据；
- 数据缺失、设定值阶跃、快速过渡等运行事件需要人工反复筛选。

本项目通过“分块导入、按日分区、服务端查询与抽稀、智能分段”的方式，将历史数据转化为可浏览、可比较、可导出的分析结果。

## 三、项目目标

### 3.1 总体目标

形成一个可在局域网内部署的 PID 历史数据分析工作台，使使用者能够从文件上传开始，在较短操作路径内完成数据浏览、趋势分析、运行事件定位和结果导出。

### 3.2 具体目标

1. 支持 CSV、XLSX 文件导入，自动识别时间列和常见 PID 信号类型。
2. 支持大文件分块读取和后台导入，避免整文件常驻内存。
3. 按自然日建立数据分区，支持年度运行日历和单日浏览。
4. 支持全天、6 小时、3 小时、1 小时、30 分钟、15 分钟等日内窗口移动查看。
5. 通过服务端抽稀和最小/最大值保留，控制图表返回规模并尽量保留尖峰。
6. 自动识别设定值变化、PV/MV 快速变化、振荡、稳定段和数据缺口等运行片段。
7. 支持当前时间窗口 CSV 导出，并为后续接入更大规模数据库保留接口。

## 四、目标用户与使用场景

### 4.1 目标用户

- 工艺工程师、仪表工程师和控制工程师；
- 需要复盘历史运行状态的生产和设备管理人员；
- 进行控制回路整定、异常分析和数据质量检查的技术人员。

### 4.2 典型使用流程

1. 用户打开局域网地址并上传一份 CSV/XLSX 历史文件。
2. 系统显示上传进度，后台显示行处理进度；导入完成后数据集才进入列表。
3. 用户选择数据集、年份、回路和 PV/SV/MV 信号类型。
4. 在年度日历中选择某一天，查看完整率、分段数量和年度趋势。
5. 进入单日页面，通过时间滑块移动到具体时段，查看同步曲线和智能分段。
6. 按需导出当前窗口数据，用于报告、复盘或进一步分析。

## 五、总体技术方案

### 5.1 系统架构

```text
浏览器（年度日历 / 单日曲线 / 时间窗口）
              │ HTTP API
FastAPI + Uvicorn（上传、任务状态、查询、分段、导出）
              │
导入层：CSV 分块 / XLSX 只读迭代 → 时间与信号标准化
              │
存储层：Parquet + DuckDB（默认）
      PostgreSQL（可选，面向大规模数据）
      ClickHouse（兼容路径）
```

### 5.2 数据标准化

统一记录字段为：`dataset_id、timestamp、tag、type、value、quality、unit`。时间戳按 Asia/Shanghai 的工厂本地时间处理；无效时间会被剔除并写入警告信息。包含 PV、SV/SP、MV 的列名会自动归类，其他数值列保留为 `other`。

### 5.3 性能与容量策略

- 上传默认上限为 2048 MiB，可通过环境变量调整；多个上传任务并发导入，默认并发数 2，可由 `PID_IMPORT_WORKERS` 调整；
- CSV 使用分块读取并支持 UTF-8（含 BOM）/GB18030/GBK/UTF-16 编码识别，XLSX 使用只读行迭代；
- Parquet 按 `date=YYYY-MM-DD` 分区；
- 查询按时间和信号过滤，图表默认按 1 分钟、10 秒或自动分辨率返回；
- 每个信号的图表数据目标上限为 5000 点，并保留桶内极值；
- PostgreSQL 模式采用批量 COPY 和索引查询；ClickHouse 保留按月分区的兼容路径。

## 九、实施计划

### 阶段一：基础功能固化

完成文档、接口契约、异常处理和样例数据流程整理，确保本地 Parquet 模式稳定运行。

### 阶段二：数据规模与性能验证

### 阶段三：算法与交互优化

使用真实 PID 样本校准分段阈值，补充分段统计和人工修订；增加浏览器端回归测试，覆盖上传失败、空日期、窗口边界和导出；进一步验证流式导出在 GB 级窗口下的内存表现。

### 阶段四：部署交付

完成 Plotly 静态资源离网验证、Windows 防火墙说明、Docker 配置加固、密码和端口安全检查，并完成 PostgreSQL 模式的导入、查询与重启恢复验收，形成试运行版本。

## 十、风险与应对措施

| 风险 | 应对措施 |
|---|---|
| 超大文件导入耗时长 | 分块读取、后台任务、进度反馈；生产环境使用 PostgreSQL |
| 工业数据列名不规范 | 提供手动映射；保留 `other` 类型并在导入报告中提示 |
| 分段误报 | 阈值参数化，使用现场样本评估并保留人工修订能力 |
| 局域网无法访问 | 绑定 `0.0.0.0`，检查 TCP 8080 防火墙规则和服务器 IP |
| 数据库配置不当 | 使用环境变量提供密码，限制数据库端口访问范围并保留 Parquet 回退 |
| 完全离线时图表资源不可用 | 将 Plotly.js 纳入静态资源并增加启动自检 |
